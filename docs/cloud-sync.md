# 云存档同步

**这篇讲什么**:双引擎(kopia 快照 / rclone 一版一 zip)怎么选、存档以什么形状躺在 B2 里、**游戏身份(指纹 + 配对)怎么认「哪一条是本机这一款」**、云端索引一份与它在本机的那份缓存、三个动作语义为什么不同、凭据的存储与挑选顺序。

**什么时候读它**:改同步行为、引擎或凭据后端；改配对 / 身份 / 索引;排查「存档没上传 / 传错了 / 恢复没生效」。

核对来源:`src/sync/**`、`src/daemon/sync_rpc/`、`src/secrets/`、`src/config/sync.rs`、`tests/ipc_e2e/`、`tests/portable_ipc/`。

---

## 1. 两个引擎,一个门面

`SyncConfig.engine` 选引擎,**全局一个,不是每个游戏一个**:

| 引擎 | 形态 | 加密 | 默认 |
|------|------|------|------|
| `kopia`(要求 ≥0.22) | `<prefix>/kopia`,内容寻址仓库,一版一个快照 | **自带加密**(仓库密码默认 `kotori`) | ✅ |
| `rclone` | `<prefix>/games/<cloud_dir>/<stamp>.zip`,一版一个完整 zip(身份卡与包并排) | **不加密**,落桶即明文 | — |

- 两个引擎在桶里**各写各的区域**,布局互不相通。同一个桶里混用只会让「有些存档看不见」变成一件要靠猜的事。换机器(双系统)也必须选同一个。
- 上层只说「这一版」,不关心它是个 zip 还是 kopia 快照;统一由门面收口,`send` / `fetch` / `versions` / `remove` 两边各自实现。
- 两边的版本名是**同一套**(`version_stamp` 的产物;kopia 把它写进快照的 description),所以「最新的一版」「保留最近 N 版」这些语义逐字相同,上层代码一行都不用分叉。

文件分工:

| 目录 / 文件 | 负责 |
|------------|------|
| `engine/` | 「这一版怎么上云、怎么取回」。`kopia.rs` + 一组 `kopia_*.rs`(参数、删除、身份、索引、解析)、`rclone.rs` + `rclone_index.rs`、`diagnostics.rs`(把引擎的 stderr 翻译成人话) |
| `archive/` | 一个包里有什么。`gather`(收集文件、排除规则)→ `pack`(打 zip)→ `unpack` → `materialize`(为 kopia 摆出目录树) |
| `runner/` | 把两者接起来。`upload` / `pull` / `restore` / `staging` / `outcome` / `identity` |
| `fingerprint.rs` `matching.rs` `pairing.rs` `selfcheck.rs` `signature.rs` | 身份那一族(§3) |
| `index.rs` `index_cache.rs` | 云端索引与本机缓存(§4) |
| `versions.rs` `snapshots.rs` | 版本名与保留窗口(§7) |
| `executables.rs` `rclone_args.rs` `rclone_env.rs` `remote_paths.rs` `save_targets.rs` `validate.rs` | 路径、参数、纯函数那一半 |

## 2. 云端布局

```
rclone:<bucket>/<prefix>/                     ← remote_root(),例:kotori:kotori-saves/kotori
├── games/<cloud_dir>/<stamp>.zip             ← 一版一个完整的包
├── games/<cloud_dir>/kotori-game.json        ← 这一款的身份卡,与包并排
├── index/kotori-index.json                   ← 云端索引:一个桶一份的并集快照
│   index/log/<machine_id>-<时间戳>.json      ← 每次写入附带的一条增量
```

rclone 那边,`games/` 下的目录名(`<cloud_dir>`)就是一个游戏;**身份卡与版本包放在同一个目录下面**。kopia 那条路上**没有目录**:整个仓库落在 `<prefix>/kopia`,一个游戏一版 = 一条 `kind:save`、`game:<cloud_id>` 的快照;身份卡与索引也各是一条快照(`kind:identity` / `kind:index`,索引快照再靠 `index:main` 或 `index:<增量名>` 区分)。

- **一版一个包,整份上、整份下**。没有「最新指针文件」这种东西:「最新的一版」就是**名字最大的那个包** —— 少一个会写坏的东西。「回到某一版」= 把那个包铺下去,不是「先铺最新的、再把当时的差量叠上去」。
- ⚠ **`cloud_dir`(云端落点)与 `cloud_id`(身份)是两件事**:两台机器给同一款游戏起的名字可以不同、本机的 id 也可以不同,但「版本放哪个目录」必须一致,否则另一台机器看不见这一台的版本。所以落点单独记,缺省 = 本机游戏 id。
- `bucket` 与 `prefix` 都来自 `[sync]`,`prefix` 默认 `kotori`。任一个为空都还能用,只是路径短一段。
- `save_key` 由存档位置的「描述」推导,不是它的下标:`<win|rel|abs>-<小写、非字母数字折成下划线、去重下划线、截断 48 字符>`。例:`%APPDATA%\Game\save` → `win-appdata_game_save`。**在 UI 里调整列表顺序不会打乱云端已有的东西**,三种类型之间也不会撞名。
- **包内结构**:每个存档位置占一个顶层目录 `<save_key>/<相对路径>`,包根有一份 `kotori-manifest.json`(格式版本 + 打包时刻 + 每个文件的 `size` / `mtime_ms` + 这一版包含哪些存档位置)。判「谁新」**只看清单里的这两个数**:zip 条目自带的时间戳只有 2 秒精度,不参与任何判断。包内路径必须干净(拦 `..` 与绝对路径),否则恢复一个被改过的包时覆盖的就不只是存档了。**包里还带一段身份**:取回与恢复都要拿它跟本机 `cloud_id` 比对,对不上就跳过/拒绝。

kopia 那条路:**整个仓库**落在一个前缀下,一个游戏一版 = 一个快照,恢复后的目录结构与 zip 里的一模一样,合并判定原样复用。列版本、算保留窗口都**只许看 `kind:save` 那一种快照** —— 仓库里混着身份与索引快照,不能把它们当成一版存档。

## 3. 游戏身份:指纹与配对

云端只有两样东西:**存档包**与**身份卡**。本机的游戏库(路径、exe 位置、缩放档案)**不上云**;两台机器要认得「我这一款」与「你那一款」是同一款,靠的是这一节的东西。

- **exe 指纹**(`fingerprint.rs`)回答「是不是同一款」:判据是文件大小 + 首尾各 1 MiB 的 BLAKE2b-256(≤ 2 MiB 的文件整份读,不能切头尾 —— 那样中间那段会被数两遍)。字符串形如 `v1:<size>:<hex>`,**形状变了就换版本号**:老指纹从此对不上任何人,而不是与新指纹碰巧相等。超过 2 MiB 的文件中间改了认不出,这是「不做整文件哈希」的另一面,也是刻意的 —— 指纹只当提议,不决定「要不要覆盖存档」。读不到 exe(盘不在、没权限)就如实返回「没有」,**绝不编一个「大概」的值**。
- **配对**(`pairing.rs`)回答「本机哪一条档案 ↔ 云端哪一条身份」。结果落在配置的 `cloud_id`(身份)与 `cloud_dir`(云端落点)上,**粘住**,只有用户能改。判错的代价是「把存档铺到错误的游戏上」,所以规矩是**宁可不动,也不猜**:指纹**唯一命中**才自动绑 —— 而且那条身份在云端还得是「一个指纹只属于一条身份」、没被本机别的档案认领;命中多条、指纹在云端有歧义、或者只靠名字 / 存档位置「像」的,一律列出来问用户。
- 用户点过「不是同一款」会记进 `cloud_rejected`:下次配对与扫描看到它在名单里,就不再自动绑回来(那条自动规则唯一的刹车),连候选都不再列。
- 每个游戏还有自己的同步开关 `sync_enabled`(默认开;关掉**只影响自动同步** —— 启动前不取回、退出后不上传;**手动**的「立即同步」「取回存档」是明确的用户动作,不受它限制),以及「配对结论」:`ok:<目标签名>`(已确认)/ `off:<目标签名>`(问过,用户选了关掉这一款的同步);`None` = 未定。**目标签名** = `v1:<引擎>:<endpoint>:<bucket>:<prefix>`(`signature.rs`,各字段都做归一化):换桶 / 换引擎 / 换 prefix 之后结论自动失效,而改保留版本数、换凭据**不会** —— 那些与「云端那一条是谁」无关。
- **指纹只在三个时刻算**,**没有**「启动时把全库 exe 读一遍」那回事:建档案时算一次;改了 exe 重算一次(**每次用户交上来都重算**,路径没变也要算:就地换了版本、打了补丁都该认出来;算不出就如实记成「还不知道」,**绝不留下一次的答案** —— 一个过期的指纹会把这一款绑到别的云端身份上);配对 / 上传前**按需补齐**(幂等,只补缺的)。
- 身份卡(`kotori-game.json`)是云端这一款的「档案」:身份 + 给人看的名字 + 认领过它的机器列表(机器 id / 机器名 / 指纹 / 存档位置 key / 用过的 exe 路径)。
- **启动游戏前的自检**(`selfcheck.rs`):目标没配齐 / 这一款开关关着 ⇒ 一个字都不做,直接启动;在**当前目标**上已确认 ⇒ 不重扫、不问,照常取回;未定 ⇒ 按指纹在**当前桶**里找一次,恰好命中一条且没被本机别的档案认领 ⇒ 静默认领并盖章;这种情况少,多半还是得**问一次**再起游戏。**自检绝不拦启动**:读云端失败按「未定」处理,用户照样能开始玩。
- **客户端没有「随手写云端身份」这条路** —— 身份与落点只有配对那一个写入口。

## 4. 云端索引与本机缓存

「云端有哪些游戏、叫什么名字」不看每一张身份卡了(kopia 那边读一张卡 = 一次 restore,200 款就是 200 趟),改成**一个桶一份的索引**:

- **逻辑上一份,物理上是「合并快照 + 未合并增量」**:`index/kotori-index.json`(kopia 是 `index:main` 那条快照)是**并集快照**,`index/log/<machine_id>-<时间戳>.json` 是每次写入附带的一条增量(名字唯一,谁也覆盖不了谁)。**写入顺序是先增量、再重写 main**:两台机器同时同步时,各自「读-改-写」同一份 main 会互相抹掉,有了增量,丢掉的那一条仍躺在 `log/` 里;崩在「写完增量、还没写 main」中间也一样不丢条目。读的时候把「main + main 里没记过的增量」合起来看。
- 索引里存的是**不常变**的东西:云端身份(名字、指纹、机器、用过的 exe 路径)+ 很轻的摘要(有几版、最近一版的名字与大小)。
- **身份卡才是真相,索引只是镜像**:索引丢了 / 坏了照着卡能重建(「深度扫描云端」就是干这个的),所以索引**读不懂时当「没有索引」处理**,绝不让它把人卡死;写失败也只记日志,**绝不许让上传失败** —— 它只是加速用的,包才是要紧的东西。
- **读的是本机缓存**(`index_cache.rs`):读云端索引本身也是一次网络往返,所以拿到一次就落本机,放在数据目录下的 `cloud-index/<目标签名哈希>.json`,先写临时文件再改名。**按目标签名分开存**:换桶之后绝不会读到旧桶的清单(那会把 A 桶的身份绑到 B 桶的档案上);读不懂 / 格式不认识 / 签名对不上 —— 一律当**没有缓存**,绝不猜。代价只是白跑一趟网络,而猜错的代价是一条错的绑定。
- 读路径(「云端存档」页进入、「自己选…」浮层、添加页的匹配)**默认只读本地**;缓存超过**一小时**、或者本地还没有缓存时才会真的去云端。「云端存档」页那颗**刷新**按钮是唯一强制联网的读。
- 后台还有两条:daemon 起来先刷一次、之后**每小时**刷一次(和「缓存多旧算旧」是同一个数);改完**同步设置**也刷一次(目标签名会变的那种改动才刷)。上传成功与「深度扫描云端」之后顺手更新缓存。
- 刷新失败时如果手上有旧缓存就**照用**,并把失败原因带给界面。
- ⚠ 索引里记的**用过的 exe 路径**只有两个用途:给人看、当搜索关键字。它**不参与任何判断**、**不写回本机配置**、也**不拿来还原本机目录**。

## 5. rclone 引擎:一版一个 zip

版本包走 `copyto`(上传一个对象)/ `deletefile`(删掉一个对象)/ `lsf --files-only`(列目录)三种调用;身份卡与索引另走 `cat`(读一个 json 对象)与 `mkdir`(幂等建前缀目录),不存在「目录对目录地合并」。

### 凭据怎么交出去

凭据**只经子进程环境**传递,绝不进 argv(`ps` 全世界可读),也不写任何配置文件:

| 环境变量 | 值 |
|----------|-----|
| `RCLONE_CONFIG` | `/dev/null`(Windows 上是 `NUL`)—— 忽略机器上任何 rclone 配置文件,包括用户自己的 |
| `RCLONE_CONFIG_KOTORI_TYPE` | `b2` |
| `RCLONE_CONFIG_KOTORI_ACCOUNT` / `_KEY` | keyID / applicationKey |
| `RCLONE_CONFIG_KOTORI_ENDPOINT` | 仅当配置里的 endpoint 非空 |

**只有这两个 B2 值**:没有同步密码、没有 crypt 层 —— rclone 这条路**不提供任何加密**,要加密就选 kopia。

**没有 region**:原生 `b2` 后端从凭据自己发现 API 主机。

**`endpoint` 的规矩**:默认留空。填了必须是完整 URL(含 `https://`);`s3.<region>.backblazeb2.com` 被**明确拒绝** —— 那是 B2 的 S3 兼容接口,和原生 b2 后端不是同一个 API,发过去只会得到费解的 404。

### 结构校验 vs 凭据校验

- `validate`:必须 `enabled`、`bucket` 非空、`endpoint` 合法。磁盘上的旧配置多带一个 `encryption` 键也能正常加载,只是下次写回不再带上。
- `validate_secrets`:**主密码文件锁着** → 报「已锁定」而**不是**「还没有凭据」;B2 两个键缺任一 → 报错。
- `sync.status` 只在 `enabled` 时把这两条的结果放进 `problem`;`ready` 还额外要求**当前选中的引擎二进制找得到**(找不到 rclone 不拦 kopia,反之亦然)。

### 失败解释

`diagnostics.rs` 把引擎的 stderr 归成几条「你该去检查什么」,并保留原文:`bad_auth_token` / `401` → keyID 是不是 Application Key ID、applicationKey 有没有复制全;`403` → 凭据有效但这个 key 没有该 bucket 权限;bucket + `not found` → 检查 bucket 名与授权;`no such host` / `connection refused` / `timeout` / `tls` → 网络 / 代理 / DNS。日志前缀会被剥掉。

## 6. kopia 引擎:内容寻址的仓库

kopia 快照的是**目录树**,而一个游戏的存档位置散在好几个地方 —— 所以这一版先按 zip 那条路的老规矩摆成一个目录(`materialize`),再对它拍**一次**快照。一个游戏一个版本 = 一个快照,回退是「恢复那一个」,不是「拼好几个」。

几个必须知道的坑:

- **连接状态**由 `KOPIA_CONFIG_PATH` 指向的那份配置决定(在数据目录下,旁边一个文件记着当时连的是哪个桶/prefix,桶或 prefix 一换就重连)。它不在时先 `connect` 再 `create`(桶里可能已有仓库,也可能没有)。
- **默认仓库密码 `kotori`**,所有端一致 —— 双系统/多机互通,「自己下载 kopia 读」的人知道该试什么。用户可以在设置页设一个更强的(留空 = 清掉并回到默认值;UI 收到标志会如实提醒「任何拿到这个 bucket 的人都能解开仓库」)。改它等于把所有老仓库锁在门外,有测试盯着。
- `snapshot delete` **默认只演练**,必须带 `--delete`。
- kopia 默认往 `~/.cache/kopia` 写日志,目录不存在时每一步都吐 write error。所以日志目录与缓存目录必须指到自己的数据目录下。
- **B2 的 keyID / applicationKey 只能进 argv**(kopia 的 b2 后端不像 rclone 那样吃环境变量注册远端),这是「秘密绝不进命令行」那条规矩唯一的、上游强制的例外;仓库密码始终只走环境变量。禁掉 kopia 自己的 keyring 是刻意的:让它去翻 gnome-keyring 会在没有桌面会话的地方报一堆用不上的错。
- 保留窗口到期要删快照时,`remove` 先按 description 找到快照 id 再删;找不到就当「已经不在了」直接返回(保留窗口是尽力而为)。

引擎二进制的查找顺序:设置页里填的位置 > 对应的 `KOTORI_*` 变量 > **kotori 可执行文件旁边** > `PATH`,两个引擎各找各的。「旁边」正是 Windows 发布包的落点:release 把官方 kopia.exe(版本锁 0.23.1)一起打进发布目录 —— Windows 上开箱即用靠的就是这一步。

## 7. 版本包:命名、识别与保留窗口

包名是整个保留策略的锚点:

- **`stamp` 形如 `%Y%m%dT%H%M%S%3fZ-<8 位随机 hex>`**(毫秒精度 UTC)。两个性质都承重:
  - 字典序 == 时间序(等长、零填充),「最新的一版」就是 `max`,裁剪就是一个排序;
  - 名字唯一(随机后缀)。从前只有秒精度,于是**同一秒内的两次上传**(游戏刚退出就点「立即同步」)谁新谁旧全看随机后缀 —— e2e 里「恢复到最新」因此拿到过上一版;毫秒精度把撞车压到「同一毫秒还要两次上传」。
- **认名字**:19 字符(毫秒)或 16 字符(秒)+ 可选后缀,`T`/`Z` 位置与数字位都要对。**秒精度的老包照样认**,所以一个旧桶升级之后不会「看不见自己的包」。列目录输出时,不像我们自己的名字一律丢弃 —— 这正是敢下刀删的前提。
- **`keep_versions` 滚动窗口**:默认 `0` = 全部保留(悄悄丢掉一份旧存档,比多占点空间糟糕得多);上限 100(`sync.set_settings` 就拒)。按字典序排序,**删最旧的**超出的那几个。**只删云端的自家包**,本地文件永远不碰,别人放进 bucket 的东西也永远不碰。

## 8. 三个动作,三种语义(不要合并)

汇报类型 `outcome.rs`:`LocationOutcome { configured, local, action, detail }`,action 六种:`uploaded` / `pulled` / `kept` / `restored` / `skipped` / `failed`。

### 上传 `upload()` —— 「我说了算」

1. 取一个当前时刻的包名。
2. 把所有**本机有**的存档位置打成一个完整包(排除规则、软链接不跟随都在 `gather` 里),再交给引擎传上云。
3. **本地没有的目录报 `skipped`,不是失败**(一台机器上只在 Windows 才有的目录很正常);整个游戏一个存档目录都没有 ⇒ **空包根本不上传**。
4. 一个位置失败不中断其余位置,但整个游戏的 `ok` 变 false 并带上第一条失败的原因。
5. 上传成功后若 `keep_versions > 0`,再跑一次裁剪,**尽力而为**:清理失败只记警告,绝不把一次成功的上传变成失败。

> 全量上传,**不做「内容没变就跳过」**。换来的是「一个包 = 一个时间点的完整存档」;想省空间用 kopia。

### 自动取回 `pull()` —— 「只取新的」

启动前自动取回。**逐文件比较、只覆盖更新的那些**这条不变量是自己保证的,不靠引擎:

1. 取「最新一版」的包名,云端从没见过这个游戏 ⇒ 每个位置 `skipped`,**不是错误**。
2. 下载包、解开、读清单。
3. 按 `mtime_ms` 逐文件比较,**只铺比本机新的**;本机更新的一律不动(`kept`)。
4. 超时预算 30s,失败只报告不拦启动 —— 但**报价必须诚实**:超时或失败要报成「没取完」,绝不报成「云端没有存档」。

期间的东西落在数据目录下的 `sync`,**不在存档目录旁边** —— 那儿多出来的临时文件会被下一次打包收进去。临时目录有 `Drop` 收尾;上次 daemon 被杀或崩了留下的残骸由**daemon 启动时清掉**(拿到进程锁之后才动手)。Windows 上尤其要紧:临时目录不像 Linux 那样有人定期扫,而这些目录可能一个几 MB、大的上百 MB。

### 手动恢复 `restore()` —— 「覆盖,且以包为准」

1. 校验 `version` 形如包名,否则直接失败,**一个引擎调用都不发**。
2. 不带 `version` = 恢复最新一版;带 = 恢复那**一版**。
3. **以包为准,本机更新的也盖掉**(用户点了「恢复」就是他说了算)。
4. **恢复前不再把本机推上云** —— 那一手(自保快照)正是从前「恢复到最新」变成空操作的根因。恢复的可撤销性由「上一版还在」保证。
5. 回退之后本机可能还剩这一版里没有的文件:**只报不删**,detail 里列出最靠前的几个。删本地数据永远是用户点头才做的事。

## 9. 什么时候会自动同步

| 时点 | 动作 | 预算 | 失败会怎样 |
|------|------|--------|-----------|
| `game.launch` 里、spawn 游戏**之前** | `pull`(只取新的) | 30s | 写进回包与日志,**照常启动** |
| 会话广播 `SessionKind::Ended` 之后 | 等 3s,再 `upload` | 每次引擎调用 300s | 记一条记录 + 警告 |
| `sync.now`(界面「立即同步」/ CLI) | `upload`(缺 `id` = 所有配了存档位置的游戏) | 同上 | 每个游戏各自一条汇报 |
| `sync.restore` | `restore` | 同上 | 逐位置报告 |
| 每次 `upload` 之后(若 `keep_versions > 0`) | 裁剪(尽力而为) | 同上 | 只警告 |

两个设计约束值得盯住:

- **同步永远不拦游戏**。取回有硬超时,任何失败都只是「报告」。
- **`Ended` 是退出后上传的唯一触发**,而它的前提是「会话真的结束了」 —— 所以退出看门狗(见 [scaling.md](scaling.md) §5)和云同步是同一件事的两半。

每个游戏「上次同步是什么时候、成没成」**只在内存**:daemon 一重启就回到「还没同步过」。它是给设置页看的状态,不是审计日志。

`sync.status` 会**现在就**试着解析每个存档位置,解析不了就报出来(盘没挂、prefix 没了)—— 比等到同步时才炸强。

## 10. 凭据的存储与挑选顺序

**策略**:默认就是**明文凭据文件(0600)**;密钥环「有就用、没有不强求」;主密码加密文件是给想更严的人的选项。绝不再要求用户为了存一个 B2 key 去输主密码或配置密钥环 —— 日常工具都是这么做的,保护交给文件权限。

挑选顺序的唯一实现是 `open_default`,从「最严」到「最省事」:

| 序 | 这一级 | 什么时候选中 | 落点 |
|----|--------|--------------|------|
| ① | **主密码加密文件** | 文件存在就用(不需要密码就能「选它」,解锁是后面的事) | `<config 目录>/secrets.json` |
| ② | **系统密钥环** | 探测通过(装了**且**在跑) | Secret Service,经 `secret-tool` |
| ③ | **明文凭据文件**(默认) | 上面两条都不成立 | `<config 目录>/credentials.json` |
| ④ | **内存** | 连文件都写不下去 | 进程内,退出即失 |

认得的密钥只有三个:B2 keyID / B2 applicationKey / kopia 仓库密码。kopia 密码是存量用户会读到的新东西:它**有默认值**,清空 = 回到默认。

几条硬性规矩:

- **「装了」 ≠ 「在跑」**:必须真发一次查询(查一个不可能存在的 account)才算数。容器/最小桌面里 `secret-tool` 在、D-Bus 上没人应答,这时**不能**报「密钥环可用」,也不能把读取失败伪装成「没存过」。
- **② 接管时会把明文搬进去**:逐条写进密钥环,**全搬完了才删**明文文件;搬不全就保留明文 —— 宁可留一份明文,也不能让凭据凭空少一条。
- **「锁定」与「没存过」必须分开**:锁着时校验报「已锁定,请先用主密码解锁」。
- **凭据绝不写进 `config.toml`**。
- **绝不自研密码学**:主密码文件用 RustCrypto 的 Argon2id(m=19MiB, t=2, p=1)+ ChaCha20-Poly1305,信封头作为 associated data 参与认证(防降级)。
- **密码用户自设,我们绝不生成**;最短 8 个字符。
- **取回提示跟着当前生效的那一级走**:密钥环给 `secret-tool lookup …`;明文文件说「你自己打开就看得见」;主密码文件说「只有主密码,忘了就只能删掉重设」。说错比不说更坏。

### 明文凭据文件

- JSON 是 `{"<account>": "<value>"}`。
- **创建时就带 0600**(不是先建 0644 再 chmod,那会留一个窗口);读到更宽的权限**就地收紧并警告**。
- 写入是**原子的**:同目录临时文件 + `rename`。
- **坏文件是错误,不是「空」**:解析失败必须响亮地失败,否则用户会以为凭据丢了去重填。

### 主密码加密文件

- `lock()` 只丢掉内存里的密钥,文件不动;`create()` 同时用于首次设置与改密码(整份重新封)。
- daemon 侧:设置主密码时把当前生效存储里的所有条目封进文件,并**接住刚刚封好的那个句柄**(新开一个会是锁着的);清除主密码**不需要先解锁** —— 忘了主密码时它是唯一出路。

### Windows 现状

只有 Linux 的 Secret Service 后端实现了;`Keyring::system()` 在非 Linux 上返回「后端不支持」,于是按顺序落到**明文文件**(Windows 上是 `%APPDATA%` 的用户 ACL)。Windows 凭据管理器后端**尚未实现**。取回提示也**不会**把 Windows 用户指去凭据管理器 —— 那里现在没有条目,承诺一条不存在的取回路径更坏。

## 11. 云端的删除

三个删除动作,都按**云端落点**收参数(与列云端版本同一把尺子),所以「云端有、本机没有」的游戏也清得掉。**用户的显式删除不许走引擎那条「找不到就静默成功」的兜底路**(那是给保留窗口用的):删一个不存在的版本名要明确报错。

| 动作 | 结果 |
|------|------|
| 删掉某一版 | 只删这一版,本机不动,词条留着 |
| 清空这一款 | 这一款的存档全没了,**词条留着** —— 之后同步还传到同一条身份 |
| 删掉词条 | 这条身份连它的全部存档一起删,不留没人认领的数据 |

⚠ **云端一变,索引要改两处**:桶里那份**和**本机缓存(外层列表读的是后者,只改前者就会「删完退回列表还是旧版数」);词条删掉之后那一条要**整条隐掉**(索引只会增/改、不会减)。rclone 那边还要把空目录收掉,否则实时列目录那条路会把它当成「一款 0 版的游戏」。

界面上的分工:**「云端存档」页**是管云端的工具,不关心这台机器装没装那一款,三个删除入口都在那儿;**单游戏设置的「云存档」组**是本机 ↔ 云端的交互(参与开关、绑的是哪一条、立即同步 / 恢复、覆盖本机),清空与删词条也在那一块的云端清理区。**云端存档页不放任何本机动作。**

## 12. 已知未做

- **真实的 B2 闭环没跑完**:上传 → 留版本 → 滚动删除 → 回滚,本机用假引擎测过(真搬文件、断言桶内容),CI 上跑通了真 kopia 本地仓库与真 rclone 的契约;但真实 B2 账号上的完整往返没有实测。
- **kopia 的 B2 仓库往返没实测**:含密码失效、目标变更后的重连。测过的都是本地目录仓库与假二进制。
- **云端存档管理只有删除**:浏览与三个删除都接好了,**下载某一版 / 导出 / 备注 / 保留策略还没有**。单游戏侧有「替换」与「取回」,仍没有版本选择器。
- **`game.update` 换 exe 到别人在用的那一条没有检查**;两台机器给同一款游戏起了不同的云端落点时不猜也不提示。
- ⚠ **第 ④ 级(内存)只在测试里出现**:`open_default` 永远返回「不用重试」,所以「密钥环后来起来了 → 把内存里的凭据搬过去」那段逻辑在生产路径上不可达。后果:先在无密钥环的会话里存了明文,再回到有密钥环的会话,凭据要等 daemon 重启才会迁移。
- **Windows 的完整同步往返没有实测**:IPC、单实例锁、UI、单测都验过了,缺的是把两台机器用同一个 bucket 跑通一遍。

没有实测过的部分:B2 原生后端在真实账号上的端点发现行为、kopia B2 仓库的往返、Windows 的 `%APPDATA%` ACL 是否等价于 0600 —— 都只从代码与注释推断。
